# 「一账」V1.1 增量 PRD（5 项）

> **定位**：在 V1.0（`01-PRD.md` + `02-ARCHITECTURE.md`）之上**只做加法**，任何已上线 P0 行为不允许改变。
> **语言**：中文｜**平台**：iOS 17.0+｜**技术栈**：沿用 SwiftUI + SwiftData + Swift Charts，零第三方依赖。
> **前置已核实**：`Todo` 无系列字段且下一期**只在完成时**生成；`StatisticsCalculator` 有 totals/monthlySeries/categoryShares/breakdown/trend/snapshot，**无**同比与账户聚合；`ExpenseComparison`「较上月」已上线；账目软删只有 `deletedAt`，无清理与 UI；模板零实现；`LedgerEntry` 无确认状态字段。
> **结论**：需 **Schema V2，迁移为隐式 lightweight**（`stages = []`）。**不要"顺手"补一个显式 `.lightweight` stage**：`SchemaV1` 与 `SchemaV2` 引用的是同一批 `@Model` 类，`Category.templates` / `Account.templates` 的 `inverse:` 会把 `EntryTemplate` 一并拉进 V1 的 CoreData 模型，于是两版校验和逐字节相同，CoreData 直接抛 `Duplicate version checksums detected` 崩溃。三组探针的实测矩阵见 `YiZhang/Core/Persistence/SchemaV1.swift` 文件头。仅 2 项改 schema，且都是「加字段 / 加实体」，不删不改既有字段。

## 2. F-SUB-13 订阅类账目「待确认」状态

*场景：月初会员自动续费，我换了张卡、不确定到底扣没扣。App 替我记了一笔，但这笔钱我还没核对过——它不该和「我亲手记的午饭」长得一模一样。*

### 2.1 交互流程
| 位置 | 元素与点击路径 |
| --- | --- |
| 账本行 | 金额右侧琥珀色徽标「待确认」；整行仍可点进详情 |
| 首页概览卡 | 有 pending 时第三行拆两行：`较上月 ▲12.4%` / `含待确认 3 笔 ¥68.00 ›`（点 → 账本筛选到待确认） |
| 账本列表顶部 | 行动条 `3 笔待确认 · 一次性确认 ›`，可点「×」当天不再显示 |
| 账目详情 | 顶部两按钮：`这是对的`（主）/ `不是这笔`（次）；确认后消失 |
| 待确认汇总页 | 从上两处进入；底部 `全部确认`（**不提供**「全部否定」） |
| 筛选 | 新增独立 chip `待确认`（与来源筛选并列，可单独移除） |

### 2.2 状态与字段语义
- 新增 `LedgerEntry.confirmRaw: String = "confirmed"`，取值仅 `confirmed` / `pending`；计算属性 `isPending`。
- **字面量默认值 `"confirmed"`**：既有账目与新版本无关地保持「已确认」——这就是「只做加法」的落地方式。
- 生成规则（唯一实现位置：`SweepAction.draft` / `LedgerService.create` 的草稿定型处）：
  `source == subscription` 且 `occurredDay >= 今天 − 7 天` → `pending`；账期更早（冷启动补漏、补录历史）→ 直接 `confirmed`；`manual` / `todo` → 恒 `confirmed`（待办完成确认条本身即一次确认）。
- 确认：`confirmRaw = "confirmed"` + `updatedAt = now`，无其它副作用。
- 否定：等价于**删除该账目 + 抑制该周期**，复用现有 A 分支（`LedgerWriter.softDelete` + `SubscriptionService.suppress(cycleKey:)`），账目进「最近删除」，`nextBillingDay` 不回退；同周期再次否定为 no-op。
- **计入口径：pending 计入一切**（余额、首页概览、统计），理由见 Q1。

### 2.3 边界情况（逐条结论）
1. **是否计入账户余额**：计入。余额是 `initialBalance − Σ支出 + Σ收入 …` 的硬不变量（R-ACC-1），排除 pending 会让余额与银行卡对不上，比「多算 68 元」严重得多。
2. **超时未确认**：不自动确认、不自动删除、不发催办通知。一笔账的「事实性」只能由人决定；自动确认会在用户不知情时把不确定的钱变成确定，自动删除则静默丢账。pending 可无限期存在。
3. **订阅被删除后**：其 pending 账目仍为 pending，确认/否定入口照常可用（不依赖 `Subscription` 存在）；否定时找不到订阅 → 降级为**纯软删**（不写抑制表），不报错。
4. **pending 被编辑**：允许改金额/分类/账户/日期/备注，`confirmRaw` **不变**（编辑 ≠ 确认）；来源字段仍不可改（R-EDIT-1 不变）。
5. **pending 被删除**：走普通软删，**不写抑制表**。与否定区分：删除是「清理界面」，否定是「这一期没扣」，要表达后者应点「不是这笔」。
6. **幂等与同步**：`confirmRaw` 不参与 `sourceCycleUniqueKey`，待确认不影响去重（连续扫描 5 次账目数不变）；多端同时确认/否定因操作幂等，后写覆盖结果一致，无需冲突解决。
7. **导出**：CSV 新增末列「确认状态」（`已确认`/`待确认`），JSON 每 entry 新增 `"confirmation"`；`schemaVersion` 仍为 1（只加字段，旧文件可读）。
8. **统计页**：pending 计入合计，分类环不单独拆项；标记只在账本首页与详情页露出，避免图表变复杂。

### 2.4 验收标准
- 某订阅 `nextBillingDay` 设为 3 天前 + 冷启动 → 生成 1 笔 `confirmRaw == "pending"`，首页显示「含待确认 1 笔 ¥X」。
- `nextBillingDay` 设为 60 天前（≤24 期）+ 冷启动 → 生成的全部为 `confirmed`（补漏不打扰）。
- 对 pending 点「这是对的」→ `confirmRaw == "confirmed"`、徽标消失、**概览卡总额数字不变**。
- 对订阅 pending 点「不是这笔」→ `deletedAt != nil` 且该订阅 `suppressedCycles` 含该 `cycleKey`；再扫描不再生成该期。
- 手动记一笔 → `confirmed`；CSV 含「确认状态」列且既有导出用例全绿。

## 3. F-ACC-16 统计同比环比 + 账户支出构成

*场景：「今年 11 月比去年 11 月多花了多少？」「这个月是支付宝花得多还是信用卡？」——现有三图回答不了，我需要两个数字和一张按账户的横条。*

### 3.1 交互流程
- 统计页在三张卡**下方**追加两张（顺序：分类占比 → 累计趋势 → **同比环比** → **账户构成**）。
- **同比环比卡**：主数字 `本月至今 ¥3,482.50`；下方两个 chip `同比 去年同月 ¥2,980 ▲16.9%` / `环比 上月同期 ¥3,120 ▲11.6%`，chip 下方小字给出实际区间 `去年 11 月 1–20 日`。
- **账户构成卡**：横向条形（账户名 + `¥X` + `占 32%`），最多 6 条 + 「其他」合并；点某条 → 下钻账本并自动套用该账户 + 当前时间范围（复用现有筛选通道）。
- 顶部 `支出/收入` 切换时两卡跟随口径（与分类占比一致）；`本月/上月/本年` 切换时口径见 3.3-6/7。

### 3.2 口径与新增纯函数
- 全部接在 `StatisticsCalculator` 上，输入 `[LedgerLite]`（**已含 `accountID`，无需改模型**），输出值类型；零数据库、可单测。
- `struct PeriodComparison { current, baseline: Money, direction, magnitudeThousandths }`——复用 `ExpenseComparison` 的 `.unavailable/.flat` 语义与 `percentText`，**不新造百分比规则**。
- `static func comparison(_:metric:today:) -> (yoy: PeriodComparison, mom: PeriodComparison)`
- `static func accountShares(_:metric:range:today:limit: Int = 6) -> (shares: [AccountShare], mergedIDs: Set<UUID>)`，`AccountShare` 与 `CategoryShare` 同构。
- 三条不变量写死：①`type == .transfer` 跳过；②`isCountable == false`（软删 / 金额≤0）跳过；③区间用 `Int32` 日键/月键，禁 `Calendar`。

### 3.3 边界情况（逐条结论）
1. **同比区间**：主口径**同期对齐**——`本月 1 日…今天` vs `去年同月 1 日…同一天`；去年同月天数不足（本月 31 日、去年 30 天）时基线取到该月最后一天，chip 显示实际区间。
2. **分母为 0**：基线 0 且本期 >0 → 显示 `新增`（不显示 `+∞%`）；两者皆 0 → `—`；沿用 `.unavailable` 分支。
3. **数据不足一年**：不特殊处理、不显示「数据不足」。去年同月无可计账目 → `去年同月无数据`（与「上月没有支出」同句式）。首年用户看到的是一句诚实的空态，而不是错误的 -100%。
4. **与首页「较上月」的关系**：首页 `较上月` **原样不动**（已上线行为不许改）。统计页环比用同期对齐，月中可能与首页数字不同 —— 用 chip 文案「上月同期」消除歧义，而不是去改首页。
5. **账户构成 × 转账**：转账不计入任何账户的支出构成。否则从储蓄卡转 5000 到支付宝会让两账户各虚增 5000、合计翻倍。
6. **「本年」档**：同比卡改为 `本年至今 vs 去年全年同期`；账户构成卡显示本年至今。
7. **「上月」档**：同比卡显示 `上月 vs 去年同月`（整月对整月，无对齐问题）。
8. **账户已删除（`accountID == nil`）**：并入「未知账户」一条（`isMerged == false` 的哨兵，复用「无分类」处理），保证 `Σ账户 = 同口径合计`。**归档账户**：本月有账目则照常出现（行尾灰字「已归档」），无账目则隐藏。
9. **一致性断言**：`Σ accountShares.amount == snapshot.categoryTotal`，偏离即 bug（单测覆盖）。

### 3.4 验收标准
- 造 2024-11 支出 ¥1000、2025-11 支出 ¥1500（今天 2025-11-20 时已发生 ¥1200）→ 同比基线为 ¥1000、本期 ¥1200，chip 含 `去年 11 月 1–20 日`。
- 去年同月零账目 → `yoy.direction == .unavailable`，文案「去年同月无数据」。
- 造 2 账户 + 1 笔转账 → `Σ accountShares.amount` 不含转账且等于 `snapshot.categoryTotal`。
- 软删一笔支出 → 两卡金额同步减少。
- 沿用 D3 门槛：**10 000 条账目下整页聚合 < 500ms**（含新增的同比环比与账户构成两次聚合）。
  > 口径备注：原稿写「4000 条 ≤ 80ms」，但 80ms 在 XCTest 里测不出来（首帧含 UI，不可复现），
  > 且 CI 机器负载波动会让它变成随机红灯。实测装置是
  > `Acceptance_PerformanceTests.testD3b_StatisticsOverTenThousandEntries`（取全库 10 000 条，
  > 分别计时 `snapshot` / `comparison` / `accountShares` 并断言三段合计 < 500ms）。
  > 阈值要防的是「有人写出 O(n·m)」，不是机器跑分。

## 4. F-TODO-11 重复待办「删除此次及以后」

*场景：「每天喝水」坚持三个月不想做了。现在只能删今天这条，明天它又冒出来——我得一直删下去。*

### 4.1 交互流程
- 待办行「⋯」菜单（现为 `移到明天 / 删除`）在**重复且未完成**时改为三项：`移到明天` / `删除这一期` / `删除此次及以后`（destructive，置最下）。
- 选「删除此次及以后」→ 确认弹层：标题 `不再重复？`，正文 `「每天喝水」以后不会再出现。已完成的历史记录会保留。`，按钮 `删除并且不再重复` / `取消`。
- 完成后返回列表 + 3 秒 Toast `已停止重复 · 撤销`。
- 已完成历史行菜单只有 `删除这条记录`，弹层正文补一句 `重复设置不会被修改`。

### 4.2 语义（为什么不需要系列 ID）
- 下一期**只在「完成」那一刻生成**（`spawnNextOccurrenceIfNeeded`），因此任一时刻一个重复系列里**最多一条未完成行** + 若干已完成历史行。
- 所以「以后」= **还没生成、今后也不会再生成**，不需要枚举未来期，也不需要系列标识：
  - `删除此次及以后`（作用于未完成期）= 硬删该行 + **不生成下一期**。
  - `删除这一期`（作用于未完成期）= 硬删该行 + **立即生成下一期**（`dueDay` 按 `CycleAdvancer` 推进一期），系列延续。
- 已完成历史行永不参与上述操作——它们已经花过钱/办过事，是历史事实。

### 4.3 边界情况（逐条结论）
1. **「以后」如何界定**：不存在的期天然不处理。实现就是「删当前条 + 不走 spawn 分支」，不写抑制表、不落任何标记。
2. **已完成历史期**：一条不动，`status` 与 `linkedEntryID` 不变，也不因系列终止改变分组归属。
3. **误删能否恢复**：只做 3 秒内存撤销（恢复被删行；若为「删除这一期」则同时删掉刚生成的下一期），**不引入待办软删字段**。理由：待办是「未来要做的事」，误删代价是重打一遍标题；加 `deletedAt` 会让 `openTodos` 查询、计数、提醒全多一层过滤，收益不匹配。
4. **在最后一期上选「删除这一期」**：仍生成下一期（系列继续）——这是它的定义。要停止必须用「删除此次及以后」，两个选项的弹层正文必须写清差异。
5. **已完成行误以为能停系列**：菜单不提供该项，且弹层明说「重复设置不会被修改」，从入口消除误解。
6. **提醒**：删除未完成期必须取消该待办本地通知（R-TODO-05 既有规则），否则会出现「待办没了但通知还在响」。
7. **订阅扣费只读分组 / 只剩历史行的系列**：前者不参与本功能（不是 `Todo`、无菜单）；后者表现为若干「已完成」条目，属正常，不做特殊清理。

### 4.4 验收标准
- 建「每 1 天」重复，完成 3 次后对未完成期选「删除此次及以后」→ 该行消失，重启 App **不再出现新期**，已完成 3 条仍在。
- 同场景选「删除这一期」→ 该行消失但列表出现一条下一期（`dueDay` = 原 `dueDay` + 1 天）。
- 已完成行菜单无「删除此次及以后」，无法触发系列终止。
- 删除后待办的 `UNNotificationRequest` 已移除（断言 pending requests 不含该 id）。
- 3 秒内点撤销 → 行与排序恢复，系列状态与删除前一致。

## 5. F-ACC-14 常用记账模板

*场景：每天午饭都是「餐饮 ¥25 微信」。我重复选了三个月的分类和账户，其实只想点一下。*

### 5.1 交互流程
| 位置 | 元素与点击路径 |
| --- | --- |
| 记账页顶部 | 金额区上方横向 chips：`🍚 午饭 ¥25` `☕ 咖啡` + 末尾 `＋ 存为模板`；无模板时整行隐藏（不做空态占位） |
| 点 chip | 填入类型/金额/分类/账户/备注（**日期不填，永远用今天**）；已填字段被覆盖，高亮 0.3s；用户仍可改 |
| 长按 chip | `编辑 / 删除` |
| 账目详情 | 「⋯」新增 `存为模板…`（复制 type/amount/category/account/note，弹窗改名字，默认用备注或分类名） |
| 设置 → 记账设置 | 新增 `记账模板` 行 → 管理页：拖拽排序、左滑删除、点击编辑、右上「＋」新建 |

### 5.2 字段语义（新实体 `EntryTemplate`）
| 字段 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `id` | UUID | `UUID()` | 主键 |
| `name` | String | `""` | ≤20 字，非空校验在 Service 层 |
| `typeRaw` | String | `"expense"` | 复用 `EntryType` raw |
| `amount` / `hasAmount` | Int64 / Bool | `0` / `false` | `hasAmount == false` = 金额留空（只固定分类与账户） |
| `note` | String | `""` | ≤100 字，可空 |
| `sortOrder` | Int | `0` | 手动排序 |
| `category` / `account` | `Category?` / `Account?` | `nil` | 可选关系，`inverse` 侧 `.nullify` |
| `createdAt` / `updatedAt` | Date | `1970-01-01` | 审计 |

满足 CloudKit 形状：字面量默认值、无 `.unique`、无 `.deny`/`.cascade`、无可选标量（用 `hasAmount` 而非 `Int64?`）。模板**不存日期、不存来源、不支持转账**。

### 5.3 边界情况（逐条结论）
1. **上限 20 条**：满 20 时「＋」置灰并提示「最多 20 个模板，先删一个」。理由：横向 chips 一行只放 3–4 个、多了要横滑，模板价值在「一眼点到」；20 是「仍能横滑找到」的上限。
2. **金额可留空**：`hasAmount == false` 时填入**不清空用户已输入的金额**，只填类型/分类/账户/备注——这是咖啡、通勤这类「分类固定、金额每天不同」的主力用法。
3. **从历史账目存为模板**：允许，`hasAmount` 跟随原账目（金额>0 则 true）。这是最高频创建路径，必须与手动新建并列，不能只藏在设置页。
4. **分类隐藏/删除、账户归档**：逐字段降级——账户已归档 → 该字段不填、保留当前默认；分类不存在 → 该字段不填。**不弹错误**，仅在 chip 下方小字提示「模板里的账户已归档」。分类删除在 V1.0 已强制迁移（R-CAT-2），实际只会遇到账户归档。
5. **编辑/删除模板**：不影响任何已生成账目（模板是输入辅助，不是数据源；账目与模板零引用，**不存 `templateID`**）。
6. **排序稳定性**：拖拽写 `sortOrder`；chips 按 `sortOrder` + `createdAt` 排序，同一 `sortOrder` 不允许随机换位。
7. **填模板 ≠ 保存**：用户点模板后取消，不产生数据；模板优先于「上次账户 / 最近分类」（F-ACC-07），未点模板时 V1.0 默认值行为完全不变。
8. **模板名重复**：允许重名（个人自用，强制唯一只会逼用户起怪名字）。

### 5.4 验收标准
- 新建「午饭 ¥25 餐饮 微信」→ chips 出现，点击后金额 `¥25.00`、分类=餐饮、账户=微信、日期=今天。
- `hasAmount == false` 的模板在已输入 `¥88` 时点击 → 金额仍为 `¥88`，分类与账户被填入。
- 第 21 个模板无法创建且出现提示文案。
- 删除模板 → 已用该模板记过的账目数量与金额全部不变。
- 拖拽排序后重进记账页，chips 顺序一致。
- 从账目详情「存为模板」→ 管理页出现同名条目，字段与原账目一致。

## 6. 最近删除（恢复入口）

*场景：手滑删了一笔 1200 的房租，3 秒撤销早没了。我需要一个地方把它捞回来。*

### 6.1 交互流程
- 路径：设置 → `统计与数据` 区 → `最近删除`（行尾显示条数，如 `最近删除 3`）。
- 页面：按**删除日**倒序分组（`今天 / 昨天 / 11月18日`）；行 = 分类图标 + 分类名 + 备注 ｜ 金额 ｜ `原日期 11月1日` + 来源徽章 + 右尾 `剩余 12 天`。
- 行点击 → 账目详情（只读），底部 `恢复` / `彻底删除`；页面底部 `全部彻底删除`（destructive + 二次确认）。
- 空态：`没有最近删除的账目` + 副文案 `删除的账目会在这里保留 30 天`。
- 恢复成功 → Toast `已恢复`，该行消失，返回账本可见该账目。

### 6.2 状态与清理语义
- 保留期 **30 天**（按 `deletedAt` 与今天相差的自然日数，`> 30` 即过期），与 PRD §8 既有承诺一致，不新造数字。
- 清理时机：①冷启动（在既有 `Diagnostics` / `SweepCoordinator` 之后异步执行）；②每次软删除提交后。**不要求精确到时刻**，只保证「过期后最迟下次启动被清掉」。
- 过期处理 = **物理删除**（`LedgerWriter.hardDelete`），不是隐藏。理由：保留期是对用户的承诺，隐藏等于数据永久留库却永不可达——既违背承诺也白占空间。
- 容量上限 500 条：超出按 `deletedAt` 从最旧开始物理删除（兜底「误删全库」的极端场景）。
- 恢复订阅来源账目：`deletedAt = nil` 且 **`SubscriptionService.unsuppress(cycleKey:)`**（该方法已存在，正是为此场景写的）；不回退抑制的话，该期一旦被硬删就再也回不来。
- 恢复待办来源账目：只恢复账目，**不触碰 `Todo`**（待办仍已完成，`linkedEntryID` 未断则「已记账」标记自然恢复）。

### 6.3 边界情况（逐条结论）
1. **恢复后订阅会重复生成吗**：不会。账目本身占着 `sourceCycleUniqueKey`（幂等键在含软删记录的范围内唯一），扫描会跳过；`unsuppress` 只撤掉「第二道保险」，不触发补账。**这是必须断言的点。**
2. **31 天前删除的**：列表里直接看不到（已物理清除），不做「已过期不可恢复」的中间态。
3. **同一账目被删两次**：第二次软删时 `deletedAt` 刷新为最新时间，保留期从最后一次删除重新起算（用户视角：刚删的就该能恢复）。
4. **源对象已删除**：行尾来源徽标显示「订阅已删除」/「待办已删除」；恢复仍可进行，只是找不到订阅时静默跳过抑制回退，不报错。
5. **pending 账目被否定后恢复**：恢复到 `confirmRaw == "pending"`（原状态），用户可再次确认或否定，不自动当作确认。
6. **排序与分组**：固定按删除时间倒序 + 删除日分组，**不提供**按金额/原日期排序（救急页面加排序器只会增加决策成本）。
7. **技术回退条款**：若 `#Predicate` 的 `deletedAt != nil` 在目标机型不稳（架构 §3.5 已记录 iOS 17 对 `Optional<Date>` 谓词的已知问题），则加 `deletedDay: Int32 = 0` 哨兵（`0` = 未删除）。是否加由架构师实现时决定，**产品口径不变**。

### 6.4 验收标准
- 软删一笔账 → 设置页「最近删除」计数 +1 且列表可见。
- 恢复 → `deletedAt == nil`，账本与首页总额恢复为删除前数值（精确到分）。
- 恢复一笔订阅来源账目 → 该订阅 `suppressedCycles` 不再含该 `cycleKey`，且触发扫描后账目数**不增加**。
- 人为把某条 `deletedAt` 设为 31 天前 → 下次冷启动后该行物理不存在（fetch 为空）。
- 彻底删除 → 物理不存在且不可再恢复。
- 恢复后 `createdAt` / `sourceCycleKey` / `confirmRaw` 与删除前完全一致。

## 7. 待确认问题（5 条，均带推荐）

**Q1｜待确认账目是否计入首页总额与统计？** 推荐：**计入**，同时露出「含待确认 ¥X」。
理由：①金额余额是 `initialBalance − Σ支出…` 的硬不变量，排除 pending 会让余额和银行卡对不上；②「统计数字自己变了」是记账 App 最致命的信任崩塌，让总额稳定、另给小计更安全；③点确认该是「补一个安心」，不该是「改一个数字」。代价是极少数情况总额偏高，但有可见小计可自查。

**Q2｜同比口径：同期对齐，还是整月对整月？** 推荐：**同期对齐**，且首页已上线的「较上月」原样不动。
理由：月中用「整月对整月」会系统性显示「比去年降 40%」，纯粹因为月份没过完，是假信号；同期对齐才对应「到今天为止我比去年多花了吗」。口径不一致的风险用 chip 文案「上月同期 / 去年同月 1–20 日」消除，而不是去改已上线行为。

**Q3｜哪些订阅账目进入待确认？** 推荐：**仅「应扣日在最近 7 天内」的新账目**，补漏的历史账目直接 `confirmed`。
理由：补漏可能是三个月前的账，让用户回溯确认三个月前的扣费毫无意义，还会一次冒出十几条把首页刷满。7 天是可调常量，够覆盖「月初续费、我周末才打开 App」的真实节奏。

**Q4｜重复待办是否引入系列 ID（`seriesID`）？** 推荐：**不引入**，功能只作用于「当前未完成期」。
理由：下一期仅在完成时生成，故「以后」= 不存在，删当前条且不 spawn 即完整语义，零 schema 改动。引入 `seriesID` 唯一多买到的是「从一条三年前的历史行终止系列」——低频，且用户在当期操作是更直接的入口。

**Q5｜回收站保留期与过期行为？** 推荐：**30 天自动物理删除**，不提供「永久保留」开关、不做「仅隐藏」。
理由：30 天与 PRD §8 承诺一致；物理删除才兑现「保留 30 天」这句话，隐藏会让数据永久占库而用户以为已清空。不设开关是为了不增加一个「我上次到底设了什么」的困惑，500 条上限兜底极端场景。

## 8. 明确不做（防范围蔓延）

1. **不做** pending 的自动确认 / 自动删除 / 催办通知（含「超过 N 天自动处理」）。
2. **不做** 「全部否定」批量操作；否定必须逐条（一次误点否掉 10 期扣费无法挽回）。
3. **不做** 单笔极值（最大/平均/频次）、标签统计、年度报告——F-ACC-16 的其余部分留 V1.2。
4. **不做** 同比/环比的图表化（柱/线），只做数字；**不做** 任意月份任选对比（只做本月档与本年档）。
5. **不做** 待办软删除 / 待办回收站；「删除此次及以后」只有 3 秒内存撤销。**不做** 系列预览列表、系列整体编辑、「修改此次及以后」。
6. **不做** 模板的分组/文件夹、共享、自动推荐、使用次数统计；**不做** 转账模板、模板内嵌日期偏移。
7. **不做** 回收站纳入订阅 / 待办 / 分类 / 账户的删除（它们要么硬删、要么归档，语义不同）；**不做** 回收站的手动排序、搜索、金额筛选。
8. **不改动** 任何 V1.0 已上线 P0 行为：`ExpenseComparison`「较上月」、六维筛选、幂等键规则、余额公式、`sourceCycleUniqueKey` 语义、R-SUB-DEL 双分支。
9. **不引入** 任何第三方依赖；不新增 `#Index`（iOS 17 不支持）。
