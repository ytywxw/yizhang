## 1. 产品定义

### 1.1 一句话定义

**一款给「一个人自己用」的轻量个人财务 App：记账是主体，待办和订阅是让账目自动产生的两个入口，任何一件事最终都沉淀成一笔账。**

### 1.2 产品目标（3 个，互相正交）

| 编号 | 产品目标 | 衡量标准（可验证） |
| --- | --- | --- |
| G1 | **让记账成为打开 App 的第一动作，而不是负担** | 从冷启动到账目保存完成，点击次数 ≤ 4 次、耗时 ≤ 10 秒；记账输入页一屏完成，无需滚动、无需二级页面 |
| G2 | **让「会产生花销的事」自己变成账目，用户不记第二遍** | 订阅类账目 100% 由系统生成（用户零操作）；有花销的待办完成时，用户最多 1 次点击完成记账；V1.0 结束时「来源=订阅/待办」的账目占比可被统计出来 |
| G3 | **账目数据必须可信：看到的每一笔都是真实发生的钱** | 不做预估、不做预留、不做提前生成；任何自动生成的账目都可在 1 次操作内撤销，且撤销不会污染订阅/待办的状态 |

### 1.3 「一件事，一笔账」这条主线在产品内如何落地

这是「一账」这个名字的落点——每一件「事」，最后都落成一笔「账」——必须在界面上看得见，而不是文案口号：

1. **统一称谓**：产品内把「待办」和「订阅」统称为**「事」**。记账时是「钱」，记事前是「事」。
2. **账目必带来源徽章**：账本列表里，由订阅生成的账目行末尾有 🔁 徽章，由待办生成的账目行末尾有 ✅ 徽章；手动记账无徽章。**徽章是「这件事办完了」的视觉锚点。**
3. **账目详情页可回溯**：账目详情页固定一行「来自：订阅『iCloud 50GB』」/「来自：待办『周末买菜』」，可点击跳转到源对象。源对象已删除时显示「来源已删除」但账目保留。
4. **首页三段式呼应**：首页从上到下是「这个月花了多少（钱）」→「今天要办什么事（事）」→「今天有什么账（钱）」，形成「事 → 账」的因果阅读顺序。
5. **空状态文案统一**：账本空态写「还没有账目，记下第一件事」；待办空态写「有什么要办的？办完可以顺手记一笔」；订阅空态写「把每月固定的支出放进来，以后自动记账」。

### 1.4 明确的「不做」（定位边界）

- 不做多人协作、不做共享账本、不做家庭账户。
- 不做云同步强依赖：App 完全离线可用，无网络也能记账（这也是 V1.0 不做 iCloud 同步的直接理由）。
- 不做记账 SaaS、不做报表订阅付费、不做广告。
- 不做通用待办 App：不跟滴答清单/Todoist 竞争，不做看板、子任务（P2）、协作、番茄钟。
- 不做订阅管理工具（不聚合第三方订阅、不抓取邮箱账单）。
- 不接银行/支付宝/微信账单导入（P2 以后再说）。

### 1.5 用户画像与用户故事

**目标用户**：一个人管理自己钱的 iOS 用户；有 2～8 个周期性订阅（视频会员、iCloud、音乐、AI 工具）；日常有「带花销的待办」（买菜、加油、买礼物）；不想学复式记账，只想月底知道钱去哪了。

| 编号 | 用户故事 |
| --- | --- |
| US1 | 作为一个记账用户，我想打开 App 就在第一屏看到「这个月花了多少、还剩多少」，这样我不用点任何地方就知道自己的状态。 |
| US2 | 作为一个记账用户，我想在 3 步内记完一笔账（金额 → 分类 → 保存），这样我在便利店结账时能 10 秒内记完。 |
| US3 | 作为一个有订阅的用户，我想把「每月 25 元视频会员」录一次，之后每个月自动出现在账本里，这样我不会漏记也懒得每月手动记。 |
| US4 | 作为一个有琐事的用户，我想把「周末买菜 ¥200」记成一个待办，办完打勾时顺便确认实际花了多少，这样一件家务事直接变成一笔账。 |
| US5 | 作为一个关心支出的用户，我想看到这个月的支出构成和「比上月多花了还是少花了」，这样我知道该砍哪一项。 |

## 2. 信息架构与首页

### 2.1 底部 Tab 结构（4 个）

| Tab | 名称 | 职责边界（做什么 / 不做什么） |
| --- | --- | --- |
| 1 | **账本**（首页） | 月度概览 + 今日事/今日账提醒 + 账目流水列表 + 记账入口 + 统计入口。**这是 App 的默认落地页。**不做待办全量列表、不做订阅全量列表。 |
| 2 | **待办** | 「我要办的事」清单：待办增删改、勾选完成、提醒、重复规则、完成时记账确认。不做金额统计，不做账目浏览。 |
| 3 | **订阅** | 「我要被扣的钱」清单：订阅增删改、暂停/取消、即将扣费时间轴、每月固定支出总览。**不做订阅产生的账目列表**（那些在账本里看）。 |
| 4 | **我的** | 账户管理、分类管理、统计与报表入口、数据导出、通知与安全设置、关于。 |

> **为什么不设独立的「首页 + 账本」两个 Tab**：记账是主体，首页就该是账本。如果拆出「今日」首页，用户每次记账要多一次点击，且账本 Tab 会变得空洞。合并后的账本首页 = 概览卡 + 提醒卡 + 流水列表，一个页面承担三件事，滚动即完成信息分层。

> **为什么统计不占 Tab**：统计是「周度/月度才看」的低频页面，放在账本页右上角图标 + 「我的」里双入口即可，把宝贵的 Tab 位留给高频的订阅。

### 2.2 首页（= 账本 Tab）信息优先级与排布

用户打开 App 的第一诉求是「我这个月花了多少、花在哪」，因此**钱在事之上，概览在详情之上**。

| 顺序 | 区块 | 内容 | 优先级理由 |
| --- | --- | --- | --- |
| ① | 顶部导航 | 左「2025年11月 ▾」（月份切换）、右「📊 统计」图标 | 月份是第一上下文 |
| ② | **月度概览卡** | 主数字：本月支出 ¥3,482.50（28pt 加粗）；次：收入 ¥12,000 · 结余 ¥8,517.50；副行：较上月 ▲12.4%（红色）/▼8.1%（绿色）；点卡片进入统计页 | 第一诉求，占屏 1/3 高度 |
| ③ | **今日速览条** | 两条并列 chip：「今天要办 3 件」→ 待办 Tab；「7 天内扣费 2 笔 ¥68」→ 订阅 Tab。无内容时整条隐藏 | 「事」的入口，必须在钱之后、流水之前 |
| ④ | 账目流水列表 | 按日分组，日期头「11月20日 今天 · 支出 ¥86 收入 ¥0」，下方逐笔（分类图标/颜色 + 分类名 + 备注 + 账户 + 金额） | 主体浏览内容 |
| ⑤ | 悬浮按钮 FAB「+」 | 右下角，固定；点击进入记账输入页（默认支出）。长按 = P1「再来一笔」 | 最高频动作，常驻 |

> **排布规则的硬约束**：月度概览卡不得被任何其他卡片挤到第二屏；「今日速览条」高度不超过 44pt，不能变成第二个信息流；流水列表永远是滚动区域的主体。

### 2.3 全局导航模型

- 4 个 Tab 各自维护独立的导航栈（iOS 原生 `TabView` 行为），切 Tab 不丢失栈内位置。
- 记账输入页、待办编辑页、订阅编辑页均为 **Sheet（模态）**，从底部升起，可下拽关闭；关闭时有未保存内容需二次确认。
- 详情页（账目详情、待办详情、订阅详情）为 push 页面。

## 3. 记账模块（主体，最详细）

### 3.1 结论先行（三条需要你确认的判断）

| 议题 | 结论 | 理由 |
| --- | --- | --- |
| 是否需要「转账」 | **需要，但只做极简两账户互转（P0）** | 只要账户里存在「信用卡」，就必然有「还款」这个动作；不做转账，信用卡余额会永久性失真。但不做手续费、不做汇率、不做多币种换算。 |
| 是否需要「账户」 | **需要（P0），轻量实现** | ①订阅必须绑定支付账户，用户才能回答「这个月订阅从微信扣了多少」；②「花在哪」这个诉求里，账户是一个真实维度；③只看分类不看账户，月底无法核对余额。**但**：不做账单导入、不做自动对账、不做账户流水穿透（P1）。 |
| V1.0 是否做「预算」 | **不做**（P2） | 预算是另一个产品心智（计划 vs 事实），会和「自动记账」争夺首页信息位。V1.0 用「较上月 ▲/▼」满足「花超了没」的心理需求，成本低得多。 |

> 备选方案已在第 11 章 Q4 列出：如果你希望 V1.0 更极简，可以把「账户 + 转账」整体降到 P1，改为每笔账只记分类。我**不推荐**这样做，但这是可选项。

### 3.2 数据结构

#### 3.2.1 账目（LedgerEntry）

| 字段 | 类型 | 必填 | 约束与说明 |
| --- | --- | --- | --- |
| id | UUID | 是 | 主键 |
| type | 枚举 | 是 | `expense` 支出 / `income` 收入 / `transfer` 转账 |
| amount | 整数（分） | 是 | **以「分」为单位存整数**，禁止用浮点存金额；> 0 |
| categoryID | UUID | 是 | 转账类型的账目无分类，用系统内置「转账」占位 |
| accountID | UUID | 是 | 转账时另存 `toAccountID` |
| toAccountID | UUID | 条件 | 仅 `type == transfer` 时必填；约束 `toAccountID != accountID` |
| occurredAt | Date | 是 | 账目发生的**自然日**（不是创建时间）；手动记账默认今天，可回填过去日期；**不允许选择未来日期** |
| note | String | 否 | ≤ 100 字 |
| tags | [String] | 否 | P1；V1.0 界面不暴露，数据结构预留 |
| source | 枚举 | 是 | `manual` 手动 / `todo` 待办 / `subscription` 订阅 |
| sourceRefID | UUID? | 条件 | `source != manual` 时必填，指向待办或订阅 |
| sourceCycleKey | String? | 条件 | 仅 `source == subscription`，格式 `yyyy-MM`，用于**幂等去重** |
| createdAt / updatedAt | Date | 是 | 审计字段 |
| deletedAt | Date? | 否 | **软删除**，用于撤销与统计一致性 |

#### 3.2.2 账户（Account）

| 字段 | 说明 |
| --- | --- |
| id / name | 名称可自定义（如「招行储蓄卡」） |
| kind | `cash` 现金 / `debit` 储蓄卡 / `credit` 信用卡 / `alipay` 支付宝 / `wechat` 微信 / `other` 其他 |
| initialBalance | 期初余额（分），仅用于展示，不参与统计 |
| isArchived | 归档后不出现在记账选择器中，但历史账目保留 |
| sortOrder | 手动排序 |

- R-ACC-1：账户余额 = `initialBalance - Σ支出 + Σ收入 - Σ转出 + Σ转入`，**只读计算，不允许手改**（要改就改期初余额或记一笔调整）。
- R-ACC-2：V1.0 预置 5 个账户：「现金」「微信」「支付宝」「储蓄卡」「信用卡」，用户可重命名、可删除（删除时若有账目则改为归档）。
- R-ACC-3：**信用卡不参与「净资产」概念**，V1.0 不显示净资产，避免负债展示误导。

#### 3.2.3 分类（Category）

| 字段 | 说明 |
| --- | --- |
| id / name | 名称，同 type 下不可重名 |
| type | `expense` / `income`，**分类与账目类型强绑定**（支出分类不能用于收入账目） |
| iconName | SF Symbols 名称，从内置 40 个精选图标中选 |
| colorHex | 从 12 色品牌色板中选 |
| isPreset | 预置分类不可删除，只能隐藏 |
| sortOrder / isHidden | 排序与隐藏 |

**支出预置分类（14 个）**：餐饮、买菜生鲜、交通出行、购物、居住（房租水电）、通讯网络、娱乐、医疗健康、教育学习、人情往来、旅行、宠物、**订阅服务**、其他。

**收入预置分类（5 个）**：工资、奖金、兼职副业、投资收益、其他收入。

- R-CAT-1：**支持自定义分类**（P0）增删改、换图标、换颜色、拖拽排序；预置分类可隐藏不可删除。
- R-CAT-2：删除自定义分类时，若其下有账目，必须选择「迁移到某分类」或「归入其他」；不允许产生无分类账目。
- R-CAT-3：**不做二级分类**（V1.2 再议）。理由：移动端二级分类的选择成本翻倍，与「3 步记账」目标冲突。
- R-CAT-4：新建订阅时默认分类为「订阅服务」；新建有花销待办时默认分类为最近使用分类。

### 3.3 记账输入路径（最短路径设计）

**目标：≤ 4 次点击、≤ 10 秒、单屏完成。**

流程：首页 FAB → 记账输入页（Sheet 从底部升起，金额键盘自动弹出）→ 输入金额 → 点分类 → 点「保存」。

| 步骤 | 交互 | 默认值（关键！） |
| --- | --- | --- |
| 0 | 点 FAB | 类型默认「支出」；日期默认今天；账户默认「上次使用的账户」；分类未选 |
| 1 | 输入金额 | 自研金额键盘（0-9、`.`、⌫、`+ - × ÷` 四则运算、`今天/昨天` 日期快捷）；金额区 40pt 大字 |
| 2 | 选分类 | 首屏展示「最近使用的 6 个分类」+「全部」按钮；已选分类高亮 |
| 3 | 点「保存」 | 保存成功 → Sheet 收起 → 列表顶部插入新账目并有 0.2s 高亮动画 → Toast「已记一笔 ¥28」+「撤销」按钮（3 秒） |

- R-IN-1：**金额为 0 或空时保存按钮置灰**，必须金额 > 0。
- R-IN-2：**分类未选不允许保存**。如果用户只输了金额就点保存，自动选中「最近使用分类」中的第一个（不弹提示），保证 2 步也能完成。
- R-IN-3：备注字段默认折叠为一行占位「添加备注」，点击展开键盘；不强制填写。
- R-IN-4：收入录入：点击顶部「支出/收入」分段控件切换，分类宫格随之切换为收入分类，颜色主题变绿。
- R-IN-5：转账录入：类型选「转账」后，分类宫格隐藏，替换为「从 [账户] → 到 [账户]」两个选择器；转账**不计入收入/支出统计**。

**能力分档结论**：

| 能力 | 优先级 | 结论与理由 |
| --- | --- | --- |
| 金额键盘 + 分类快捷 + 默认值记忆 | **P0** | 核心路径 |
| 计算器（`12.5+8.8`） | **P1** | 成本低，实用（AA 分摊、加总） |
| 常用记账 / 模板（保存一组「午餐 ¥25 餐饮 微信」一键复用） | **P1** | 高频场景提效，但 V1.0 有「最近使用分类 + 默认账户」已覆盖 80% |
| 拍照 / OCR 识票 | **P2，明确 V1.0 不做** | 识别准确率与工程成本不匹配个人开发者 MVP；错误识别反而增加修正成本 |
| 语音记账 / 快捷指令 / 分享扩展 | **P2** | 好想法，但不解决 V1.0 的核心问题 |
| 长按 FAB「再来一笔相同」 | **P2** | 便宜的小惊喜，放 V1.1 |
| 记账后自动写日历 / 定位提醒 | **P2 且明确不做** | 隐私敏感，收益低 |

### 3.4 账本列表与筛选

**默认视图**：当前月，按日倒序分组。

- 日分组头：`11月20日 周四 · 支出 ¥86.00 收入 ¥0`（今天显示「今天」，昨天显示「昨天」）。
- 账目行：左（分类图标带分类色圆底）中（分类名 + 备注，两行；第二行小字为账户名 + 来源徽章）右（金额，支出黑色/收入绿色，转账灰色带箭头）。
- 底部固定：`本月支出 ¥3,482.50 · 收入 ¥12,000 · 结余 ¥8,517.50`。

**筛选维度**（右上「筛选」图标，Sheet 形式）：

| 维度 | 选项 |
| --- | --- |
| 时间 | 本月 / 上月 / 近三月 / 本年 / 自定义起止日 |
| 类型 | 支出 / 收入 / 转账 / 全部 |
| 分类 | 多选（含「未分类」不存在） |
| 账户 | 多选 |
| **来源** | 手动 / 待办 / 订阅（这是本品类特有维度，必须有） |
| 关键词 | 匹配备注文本 |

- R-LIST-1：**筛选条件以 chip 形式展示在列表顶部**，可单个移除，`清除全部` 一键复位。
- R-LIST-2：切换月份后，筛选条件中的「时间」自动跟随为对应月份，其他筛选条件保留。
- R-LIST-3：列表采用分页加载（每页 50 条），下拉刷新。月份切换时若数据量大不得白屏（需骨架屏）。

### 3.5 编辑与删除规则（重点）

- R-EDIT-1：任何账目均可编辑金额、分类、账户、日期、备注，且**不改变 source 字段**。
- R-EDIT-2：**账目 → 源对象是单向的**。编辑账目金额**不回写**订阅金额，也不回写待办预计金额。理由：账目是「已发生的事实」，订阅是「未来的约定」，两者语义不同；回写会让用户改错一次连环错两处。
- R-EDIT-3：删除采用**软删除 + 3 秒撤销 Toast**，撤销即恢复（含 sourceCycleKey 等所有字段）。

**删除「由订阅生成的账目」的确切规则**（R-SUB-DEL）：

1. 用户在账目详情点「删除」，弹出 ActionSheet，标题「这笔账来自订阅『视频会员』」，两个选项：
   - **A「只删这笔账」**（默认，推荐）：删除账目；同时在该订阅上写入 `suppressedCycles += {cycleKey}`，使该订阅**这个周期不再自动生成**；`nextBillingDate` **不回退**。
   - **B「删这笔账，并让订阅重新生成」**：删除账目；不写 suppressedCycles；`nextBillingDate` 回退到本周期起点。下次结算扫描会再次生成。
   - **C「取消」**
2. 选 A 的后果明确：账本干净，订阅继续按期扣。这正是「用户发现扣费失败想删掉这笔账」的场景。
3. 选 B 的后果：用于「我记错了周期，想重来」。

**删除「由待办生成的账目」的确切规则**（R-TODO-DEL）：

1. 删除账目**不改变待办的完成状态**（待办保持「已完成」）。弹窗提示「『周末买菜』仍是已完成状态」。
2. 若用户希望重新生成，需在待办详情点「撤销完成」（`done → open`），再勾选完成时会重新弹记账确认。
3. 删除待办本身时，**不删除它生成的账目**（账是事实），账目详情页的「来自」显示为「待办已删除」。

### 4.2 自动记账触发时机（核心规则，必须逐条确认）

**结论：到期生成 + 冷启动补漏。不做提前 N 天预生成。**

| 编号 | 规则 |
| --- | --- |
| R-SUB-1 | `dueDate := subscription.nextBillingDate`。判据以**设备本地时区的自然日**（00:00 起算）比较，不涉及时区换算。 |
| R-SUB-2 | 触发时机：**App 冷启动**、**App 从后台恢复前台**、**用户进入订阅 Tab 或账本 Tab**。三者共用一个「结算扫描（BillingSweep）」流程，扫描在后台线程执行，不阻塞 UI。 |
| R-SUB-3 | 生成条件（**全部满足**）：`status == active` 且 `autoRenew == true` 且 `nextBillingDate <= 今天` 且 当前周期 `cycleKey ∉ suppressedCycles` 且 `trialEndDate == nil 或 今天 >= trialEndDate`。 |
| R-SUB-4 | 生成动作：①创建一笔账目，`type=expense`，`amount=订阅金额`，`categoryID/accountID` 继承订阅，**`occurredAt = nextBillingDate`（用应扣日，不用今天）**，`note = "订阅：" + name`，`source=subscription`，`sourceRefID=订阅id`，`sourceCycleKey` = 应扣日所在月 `yyyy-MM`；②`nextBillingDate` **从原 nextBillingDate 推进一个周期**（不是从今天推进）。 |
| R-SUB-5 | **补漏**：若用户 3 个月未打开 App，`nextBillingDate` 落后多个周期，则**循环执行 R-SUB-4 直到 `nextBillingDate > 今天`**，一次可生成多笔（每期一笔，`occurredAt` 为各自应扣日）。**单次扫描最多生成 24 笔**，超出则停止并在订阅详情显示提示「订阅周期异常，请检查」。 |
| R-SUB-6 | `autoRenew == false`（如手动续费的健身房月卡）：到期时**不自动生成账目**，只发本地通知「『XX 健身房』今天到期，续费了吗？」，并在订阅页显示「待续费」状态，用户点「已续费」才生成账目并推进周期。 |
| R-SUB-7 | **幂等约束**：`(sourceRefID, sourceCycleKey)` 在账目表中唯一（含软删除记录）。扫描重复执行不得产生重复账目。 |
| R-SUB-8 | **周期推进规则「期末对齐」**：以原 `nextBillingDate` 为基准加周期；`month/quarter/year` 遇到目标月无该日时取该月最后一天（1月31日 + 1月 = 2月28/29日），且下下次仍从原基准推算，**不从被夹紧后的日期继续推**，避免永久漂移。 |
| R-SUB-9 | 后台生成：**V1.0 不做 BGTaskScheduler 后台生成**。理由：①App 未运行时不保证能执行，收益低；②账目对用户不存在「实时性」要求，冷启动补漏即达成最终一致；③后台任务会让功耗与调试复杂度显著上升。提醒由本地通知承担，不依赖 App 运行。 |
| R-SUB-10 | 生成后必须可感知：账本列表新条目有 0.2s 高亮；首页「今日速览」出现「有 2 笔订阅已自动记账」提示条，点击查看。**不做弹窗打断**。 |

**为什么不做「提前 N 天预生成」**：预生成会在用户实际未被扣款时虚增当月支出，直接违反 G3（看到的每一笔都是真实发生的钱）。而且预生成的账目必须引入「已扣/未扣」状态，用户要在账本里分辨两种支出，等于把复杂度从系统挪回用户。**到期生成 + 补漏** 的代价只是「用户当天不打开 App 就晚几天看到这笔账」，而这个代价对个人记账完全可接受。

### 4.3 边界情况处理（逐条结论）

| 编号 | 场景 | 规则 |
| --- | --- | --- |
| E-1 | **免费试用期** | 填写 `trialEndDate`。试用期内（今天 < trialEndDate）**不生成任何账目**；`nextBillingDate` 应等于 trialEndDate 当天（首次实际扣费日）。订阅列表显示「试用中，X 天后开始扣费」标签。 |
| E-2 | **涨价** | 订阅详情提供「修改金额」。修改只影响**未来**周期（`nextBillingDate` 及之后），已生成的历史账目不变。修改时提示「仅影响之后的扣费」。P1 提供价格变更历史时间线。 |
| E-3 | **取消订阅** | `status = cancelled`。停止生成；`nextBillingDate` 置空；从「即将扣费」移入「已取消」分组；**历史账目全部保留**。可「恢复」，恢复时要求重新设置 nextBillingDate（默认今天 + 1 个周期）。 |
| E-4 | **暂停订阅** | `status = paused`。停止生成；`nextBillingDate` 保留不动。**恢复时**：若 `nextBillingDate <= 今天`，则把 nextBillingDate 推进到「今天之后的第一个周期日」，且**不为暂停期间补账**。理由：暂停 = 当时没花钱，补账会凭空造支出。 |
| E-5 | **补录历史订阅** | 允许 `firstBillingDate` 为过去日期。保存时出现选项：「是否为已过去的 N 个周期补生成账目？」**默认不补**，用户勾选后才补（且只补最近 12 期以内）。理由：补账会污染历史月份统计，必须用户显式同意。 |
| E-6 | **同一天多个订阅扣费** | 每条订阅**独立生成一笔账**，不合并。账本中同一天分组下显示为多笔，各自带订阅徽章。理由：合并会丢失单个订阅的可追溯性，也让「取消某个订阅」的撤销逻辑变复杂。 |
| E-7 | **不规则周期（每 2 个月 / 每 45 天）** | 由 `cycleUnit + cycleValue` 表达，UI 上提供「每周/每月/每季/每年/自定义」五档，自定义档可选「每 N 天」或「每 N 个月」。自然月推进遵循 R-SUB-8 期末对齐。 |
| E-8 | **扣费失败（用户实际没被扣钱）** | App 无支付渠道，无法自动感知。规则：①生成的账目**默认视为已发生**（计入统计）；②订阅生成的账目在详情页有一个显眼入口「这笔其实没扣款」，点击即执行 R-SUB-DEL 的 A 分支（删账 + 该周期不再生成）；③V1.1 再引入「待确认（pending）」状态（订阅账目生成时标灰，用户点确认才计入统计），V1.0 不做，因为它会让每月的账目都处于未确认状态，反而增加负担。 |
| E-9 | **订阅金额为 0（免费）** | 允许 `amount = 0` 但会在保存时提示「金额为 0 将不会生成账目」；`amount == 0` 时跳过生成（仅保留提醒）。 |
| E-10 | **nextBillingDate 被用户手动改到未来/过去** | 允许。改到过去 → 下次扫描会立即补生成（受 24 笔上限约束）；改到未来 → 顺延。这是「校正」通道。 |
| E-11 | **订阅被删除** | 与取消不同：删除会移除订阅记录，历史账目的「来自」显示「订阅已删除」。建议用户优先用「取消」而非「删除」。 |

### 4.4 订阅总览（做，且是 P0）

**结论：必须做**。订阅模块的价值不只是「自动记账」，更是「看清我的固定支出有多重」，这也是订阅页存在感的来源。

订阅页顶部卡片内容：

1. **每月固定支出** = Σ 所有 active 订阅按月折算：`年付 ÷ 12`、`季付 ÷ 3`、`周付 × 4.345`、`每 N 天 × (30.4 ÷ N)`，结果取整到元，标注「约」。
2. **年度订阅总成本** = Σ 每个 active 订阅一年内的扣费次数 × 金额。
3. **占月均支出比例**（P1）：每月固定支出 ÷ 近 3 个月平均月支出。
4. **未来 30 天扣费时间轴**：按日期排列的小时间线，显示日期 + 订阅名 + 金额，并在底部显示「未来 30 天共 ¥268」。

### 4.5 订阅列表形态

- 顶部：总览卡（4.4 内容）+ 未来 30 天时间轴（可折叠）。
- 中部：**分组列表**，分三组：`生效中`（按 nextBillingDate 升序）/ `已暂停` / `已取消`。
- 每个订阅行：图标 + 名称 + 「¥25 / 月」+ 下次扣费「11月25日（5天后）」；右侧 chevron。
- 右上角「+」新建订阅。
- 行内左滑：`暂停/恢复`、`删除`（危险色）。

### 5.2 自动记账规则（推荐方案 + 理由）

**结论：完成时弹确认条，不静默生成。**

| 编号 | 规则 |

**为什么选「确认」而不是「静默生成」**：
1. 预计金额 ≠ 实际金额是常态（买菜最典型），静默生成会产生错误数据，用户要再去账本里改一次，**两次操作 > 一次确认**。
2. 静默生成无法区分「花了」和「没花」，等于强迫用户接受系统替他做的判断，破坏 G3。
3. 确认条只多一次点击（点「完成并记账」代替「完成」），且这次点击同时完成了金额校准，是**有意义的一次点击**。

- 顶部：日期分段 `今天 / 本周 / 全部`（P0 只做这三个）。
- 主体：分组列表，`今天`（含逾期用红色标记）/ `本周` / `以后` / `无日期` / `已完成`（默认折叠）。
- 每行：左侧圆形勾选框、标题、副行（截止时间 + 金额 chip「¥200」+ 重复图标 + 优先级色条）。
- 右滑（或点勾选框）→ 完成流程；左滑 → `删除` / `改期到明天`。
- 右上角「+」新建。
- 底部：`今天还有 3 件` 的统计文字。
- **订阅扣费展示区**（见 5.5）：位于列表最顶部，默认折叠为一个单行：「未来 30 天订阅扣费 3 笔 ¥168 ▾」，展开后显示只读列表项。

### 5.5 待办与订阅的关系（结论）

**结论：订阅扣费以「只读系统待办」的形式出现在待办页顶部独立分组中，默认折叠，不混入普通待办流。**

| 编号 | 规则 |
| --- | --- |
| R-MIX-1 | 待办页顶部有独立分组「订阅扣费（未来 30 天）」，默认**折叠**为一行摘要，展开后按日期升序列出：`🔁 11月25日 · 视频会员 · ¥25`。 |
| R-MIX-2 | 这些项 `isSystemGenerated == true`，**不可编辑、不可删除、不可勾选完成、无勾选框**；点击进入订阅详情页。 |
| R-MIX-3 | 它们**不出现在**「今天/本周/全部」的普通待办计数里，也不影响首页「今天要办 3 件」的数字。理由：首页计数是「我要做的事」，混入扣费会让数字失真。 |
| R-MIX-4 | 它们**不生成第二笔账**（订阅自己已经生成账目），纯展示。 |

**理由**：完全不在待办里显示，用户会觉得「我明明今天要扣钱，为什么待办里看不到」；完全混入，则待办列表被系统项污染、勾选框语义混乱。**独立只读分组 + 默认折叠**是唯一同时满足两种诉求的形态。

## 6. 三模块联动矩阵

| # | 源模块 | 触发动作 | 是否生成账目 | 账目 source | 账目关键字段取值 | 能否反向影响源对象 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 记账 | 用户手动保存 | 是（1 笔） | `manual` | 全部由用户填写 | 无（无源对象） |
| 2 | 记账 | 编辑手动账目 | 修改原记录 | `manual` | 不改 source | 无 |
| 3 | 记账 | 删除手动账目（软删） | 删除 | `manual` | 3 秒内可撤销 | 无 |
| 4 | **订阅** | 结算扫描命中到期（`nextBillingDate <= 今天` 且 active 且 autoRenew） | **是（每周期 1 笔，补漏可多笔）** | `subscription` | `amount=订阅金额`；`occurredAt=nextBillingDate`；分类/账户继承订阅；`note="订阅：{name}"`；`sourceRefID=订阅id`；`sourceCycleKey=yyyy-MM` | **是**：`nextBillingDate` 推进一个周期 |
| 5 | 订阅 | 用户删订阅生成的账目（选 A「只删这笔」） | 删除该笔 | — | — | **是**：写入 `suppressedCycles`，该周期不再生成；`nextBillingDate` 不回退 |
| 6 | 订阅 | 用户删订阅生成的账目（选 B「重新生成」） | 删除该笔 | — | — | **是**：`nextBillingDate` 回退到本周期起点，下次扫描再生成 |
| 7 | 订阅 | 暂停订阅 | **否** | — | — | — |
| 8 | 订阅 | 恢复订阅（原 nextBillingDate 已过） | **否**（不补暂停期） | — | — | **是**：`nextBillingDate` 顺延到今天之后 |
| 9 | 订阅 | 取消订阅 | **否** | — | — | **是**：`nextBillingDate` 置空、状态改 cancelled |
| 10 | 订阅 | 修改订阅金额 | **否**（不影响历史） | — | — | 仅影响未来周期 |
| 11 | 订阅 | 到期但 `autoRenew == false` | **否**（发通知，等用户点「已续费」） | — | — | 用户确认后才生成并推进 |
| 12 | **待办** | 勾选完成（`hasExpense=true`）→ 点「完成并记账」 | **是（1 笔）** | `todo` | `amount=确认金额`；`occurredAt=completedAt 当天`；分类/账户取确认值；`note=todo.title`；`sourceRefID=todo.id` | **是**：`todo.linkedEntryID` 回写；`status=done` |
| 13 | 待办 | 勾选完成（`hasExpense=true`）→ 点「不记账」 | **否** | — | — | `status=done`，`linkedEntryID=nil` |
| 14 | 待办 | 勾选完成（`hasExpense=false`） | **否** | — | — | `status=done` |
| 15 | 待办 | 撤销完成（`done → open`） | 不自动删，**询问用户** | — | — | 用户选删则删 `source=todo` 的账 |
| 16 | 待办 | 删除待办 | **否**，关联账目保留 | — | — | 账目「来源」显示「待办已删除」 |
| 17 | 待办 | 重复待办完成一期 | **是（1 笔）**，并生成下一期实例 | `todo` | 同上 | **是**：生成下一个 todo 实例 |
| 18 | 待办 | 订阅扣费系统项（只读） | **否**（订阅自己已生成） | — | — | 无（纯展示） |
| 19 | **跨模块** | 编辑任何账目金额（含自动生成的） | 修改账目 | 不变 | — | **否**：一律不回写源对象的金额/日期 |

**矩阵的三条铁律**：

1. **账目永远由「事」单向下沉，账目不回写「事」**（唯一例外是 `nextBillingDate` 推进与 `linkedEntryID` 回写这两类「状态标记」，而非金额回写）。
2. **一个周期最多一笔账**：`(sourceRefID, sourceCycleKey)` 唯一，杜绝重复。
3. **删除账目 ≠ 删除事**；**删除事 ≠ 删除账目**。两者生命周期独立，仅通过 source 字段弱引用。

## 8. 非功能需求

| 类别 | 结论 |
| --- | --- |
| **最低系统版本** | **iOS 17.0+**。理由：SwiftData 需要 iOS 17；Observation 框架需 17；截至 2025 年底 iOS 17+ 的 iPhone 覆盖率已足够高，放弃 iOS 16 可换来显著更低的持久化层开发成本。 |
| **设备形态** | **iPhone 竖屏优先，明确不支持横屏**（`Info.plist` 只保留 Portrait）。**iPad：V1.0 不上架 iPad 原生布局**，Xcode 仅勾选 iPhone，iPad 上以兼容模式（iPhone 尺寸居中）运行。理由：个人开发者的 MVP 应聚焦单一形态；一账本类 App 的 iPad 收益（大屏看图表）不足以抵消双布局的维护成本。V1.2 再评估。 |
| **尺寸适配** | 最小支持 iPhone SE 3（375×667）；所有页面在 SE 上不得出现内容截断。 |
| **数据存储** | **本地优先**：SwiftData（SQLite 落盘），完全离线可用，无网络依赖，无登录注册。 |
| **iCloud 同步** | **V1.0 不做**，推荐 V1.1 用 CloudKit 私有库开启（见 Q1）。V1.0 的补偿措施：**必须提供 CSV/JSON 导出（P0）**，缓解「换机丢数据」焦虑。存储层从第一天起就要按「未来可同步」设计（所有实体用 UUID 主键、带 createdAt/updatedAt、避免本地自增 id）。 |
| **多币种** | **P2**。V1.0 全站单一币种 CNY，金额不带符号切换，`currency` 字段在数据层预留但不暴露 UI。理由：多币种会牵出汇率、汇总换算、账户币种一致性三个大坑，与「一个人自己用、主要在国内消费」的场景不匹配。 |
| **隐私与安全** | ①不收集任何个人数据、无第三方 SDK、无埋点上报（这一点要写进 App Store 隐私声明：Data Not Collected）。②数据文件依赖 iOS 系统级 Data Protection（`NSFileProtectionCompleteUntilFirstUserAuthentication`），**不额外做应用层加密**（本地自建加密会带来密钥管理与备份恢复的额外复杂度）。③**Face ID 锁：P1**，用 `LocalAuthentication` 实现，仅在 App 从后台恢复且超过 30 秒时要求验证；强烈建议 V1.0 带上，成本约半天。 |
| **通知** | 全部使用本地通知（`UNUserNotificationCenter`），不依赖服务端推送。三类：①订阅扣费提醒（提前 N 天 09:00）；②待办到期提醒（当天 09:00 或自定义）；③（P1）每日记账提醒。通知必须可全局关闭，且在权限被拒时在设置页有可点击的「前往系统设置」引导。 |
| **性能** | 冷启动到首页可交互 ≤ 1.5s（1 万条账目以内）；账本列表滚动 60fps；结算扫描不得阻塞主线程（异步执行，完成后再刷新 UI）。 |
| **无障碍** | 支持 Dynamic Type 到 AX3 不破版；所有图标按钮有 `accessibilityLabel`；颜色不作为唯一信息载体（收入/支出除颜色外还有 `+/-` 号）；点击区 ≥ 44×44pt；分类环形图提供列表化的等价文本描述。 |
| **深色模式** | 跟随系统，全页面（含图表配色、分类色板）需双套适配；分类色在深色下需满足对比度 ≥ 3:1。 |
| **数据一致性** | 所有跨对象写入（生成账目 + 推进 nextBillingDate）必须在**同一个事务**中提交，禁止部分成功。 |
| **可恢复性** | 删除操作全部软删除 + 撤销；设置页提供「最近删除（30 天）」入口（P1）。 |

## 11. 待确认问题（需要你拍板，共 7 条）

每条我都给了推荐选项和理由。**如果你全部同意，直接回「全部按推荐」，我就让架构师开始技术设计。**

| # | 决策点 | 选项 | 我的推荐 | 理由 |
| --- | --- | --- | --- | --- |
| **Q1** | **是否做 iCloud 同步** | A. V1.0 不做，V1.1 用 CloudKit 私有库开启<br>B. V1.0 就做（首版即带同步）<br>C. 永久不做 | **A** | ①你的使用场景是「一个人一台手机」，同步不是刚需；②CloudKit + SwiftData 的同步冲突处理会显著拖慢首版，且是个人开发者最容易翻车的地方；③但**数据不能丢**，所以 V1.0 必须带 CSV/JSON 导出兜底，且数据层从第一天就按「可同步」设计（UUID 主键 + 时间戳）。V1.1 再开同步时不用重构。 |
| **Q2** | **自动记账的生成时机** | A. 到期当天生成 + 冷启动补漏（打开 App 才生成）<br>B. 提前 N 天预生成<br>C. 到期当天用后台任务（BGTask）生成 | **A** | 预生成（B）会在没扣款时虚增支出，破坏「账目=事实」；后台任务（C）不保证执行、增加功耗与调试成本，而账目没有实时性要求。A 的唯一代价是「当天不开 App 就晚几天看到」，可接受。同时 A 天然支持补漏（3 个月没开 App 就补 3 笔）。 |
| **Q3** | **删除「订阅自动生成的账目」时，订阅怎么办** | A. 只删账，该周期不再生成（默认）<br>B. 删账并让订阅重新生成<br>C. 删账但不影响订阅（下次扫描会再生成） | **A（默认），B 作为第二选项** | A 对应「扣费失败想删掉这笔账」的真实场景，且能阻止下次扫描又生成一遍；B 对应「周期记错了想重来」。C 会导致删了又出现，体验极差，**必须排除 C**。 |
| **Q4** | **V1.0 是否要「账户 + 转账」** | A. 要（5 类账户 + 极简转账）<br>B. 只要账户，不要转账<br>C. 都不要，只记分类 | **A** | ①订阅需要绑定支付账户才有「钱从哪出」；②只有账户没有转账，信用卡还款无法表达，余额永久失真。成本上转账 UI 只有一个选择器页，可接受。选 C 会让产品退化成「只有分类的流水」，月底无法核对余额。 |
| **Q5** | **待办完成时，记账是「弹确认」还是「静默生成」** | A. 弹确认条（可改金额，可「不记账」）<br>B. 静默生成账目（用预计金额）<br>C. 生成后弹 Toast + 撤销 | **A** | 预计金额≠实际金额是常态，静默生成会产生错数据，用户还得去账本改一次（两次操作 > 一次确认）；且 B/C 都无法表达「最后没花钱」，违反「账目=事实」。A 只多一次有意义的点击。 |
| **Q6** | **V1.0 是否要「预算」功能** | A. 不做（V1.2 再做）<br>B. 做简单月总预算<br>C. 做分类预算 | **A** | 预算是「计划」，和自动记账这条「事实」主线是两套心智，会抢首页信息位。V1.0 用「较上月 ▲/▼」已能满足「我花超了没」的心理需求，成本极低。先把三个模块的联动打磨到无 bug，比加第二个心智更重要。 |
| **Q7** | **iPad 与横屏支持** | A. 只做 iPhone 竖屏，iPad 兼容模式运行<br>B. iPhone + iPad 双布局<br>C. iPhone 竖屏 + 横屏 | **A** | 个人开发者，MVP 聚焦单一形态；账本类 App 在 iPad 上的增益（大屏看图表）不足以抵消双布局的持续维护成本。V1.2 再评估。 |
